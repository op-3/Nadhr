# Building Nadhr

## Windows (x64)

### Requirements

- Windows 10 or 11, x64.
- Visual Studio 2022 (Community or Build Tools) with the
  **Desktop development with C++** workload.
- Windows SDK **10.0.28000.0** with the *Debugging Tools for Windows* feature.
  The CI installs it with the same command used in
  [`.github/actions/prepare/action.yml`](../.github/actions/prepare/action.yml).
- Python 3.12 or newer, plus `pip install httplib2==0.22.0 clang==21.1.7`.
- Git, and 7-Zip (found through the registry; or pass `--7z-path`).
- **Disk:** about 120 GB free. The source tree is roughly 35 GB and the
  output directory 50 to 70 GB.
- **Memory:** 16 GB minimum, 32 GB recommended.
- **Time:** many hours. A 10-core, 15 W laptop CPU can take well over 12 hours
  for a full official build. An incremental rebuild after a small patch is much faster.

The build uses its own LLVM, Rust and Ninja downloads (checksummed in
ungoogled-chromium-windows' `downloads.ini`), not Google's toolchain.

### Steps

```powershell
git clone --recursive https://github.com/op-3/Nadhr.git
cd Nadhr
python -m pip install httplib2==0.22.0 clang==21.1.7
python platforms\windows\build.py            # full build
python platforms\windows\build.py -j 8       # limit parallel jobs
```

Packages are written to `build\dist\`:

- `nadhr_<version>_windows_x64_installer.exe`
- `nadhr_<version>_windows_x64_portable.zip`

`--tarball` builds from Chromium's source tarball instead of a git clone. The
tarball lacks PGO profiles, so the result is slower; use it only when cloning
is not possible.

### Rebuilding after changing a Nadhr patch

Patches are applied once, when `build/src` is created. After changing a patch,
either delete `build/src` (slow, safe), or revert the old patch and apply the
new one inside `build/src` by hand, then rerun ninja:

```powershell
cd build\src
third_party\ninja\ninja.exe -C out\Default chrome
```

### CI builds

All full builds run on free GitHub-hosted runners (`windows-2022`, 4 vCPUs,
16 GB RAM). One job is limited to 6 hours, so builds run as chained stages:
each stage compiles for up to 3.5 hours, then hands its tree to the next stage.
Both build workflows are generated by `devutils/generate_workflows.py`; edit
that file, not the YAML. CI checks that they are in sync.

### Four kinds of build

| Kind | Workflow | Use it for | What it does |
|---|---|---|---|
| **Fast validation** | `validate.yml` (every push and PR) | docs, patches, strings, policies, Python and CI tooling | patch application against pinned Chromium, translation-safe branding, unit tests, threat-list tests, build-state archive round trip on Windows. Minutes. |
| **Development** | `build-dev.yml`, manual | iterating on native changes | component build, no PGO/LTO, `chrome` target only. Restores the latest dev tree built on `main`, re-patches only the files whose patches changed (`utils/tree_state.py`), recompiles only what depends on them, and smoke-tests the browser in place. `seed=true` builds a dev tree from scratch. |
| **Integration** | `build-windows.yml` on a branch, manual | testing an assembled feature before merging (for example PR #2) | the full official build, packaged and smoke-tested |
| **Release** | `build-windows.yml` on a `v*` tag | distributable binaries | as integration, plus release checks ([RELEASE.md](RELEASE.md)) |

Development builds need a full rebuild ("seed") when a base input changes: the
upstream submodules, `downloads.ini` files, pruning or substitution lists,
`name_substitution.py`, `prepare_ublock.py` or `resources/ublock/`. They then
fail with an explicit message. Only `main` publishes the dev tree
(`dev-tree` artifact, kept 7 days), so run a dev build on `main` at least weekly.

### Measured CI timings

Release build run 45891287269 (2026-11-26 to 28, `-j 2`, before these changes):

| Part | Time |
|---|---|
| Total | about 38 h |
| Stages 1 to 8 | about 4.5 h each: 3.5 h compiling, about 1 h restoring and re-uploading the 18 GB tree (7-Zip zip) |
| Stage 9 | finished the compile and packaged |
| Stages 10 to 16 | 2 to 3 min each of setup with nothing left to do |

Changes made after that run, **not yet measured**:

- 4 parallel compile jobs (was 2) with `concurrent_links=1` to keep links
  within 16 GB RAM.
- tar with multi-threaded zstd for the tree hand-off, falling back to 7-Zip.
  Every transfer step logs a `[timing]` line.
- Stages after the build has finished skip all setup.
- Incremental development builds (above).

Results will be recorded here from real runs.

## Checking patches without building

```sh
python devutils/validate_patches.py            # series consistency only
python devutils/validate_patches.py --remote   # apply against Chromium at the pinned tag
python devutils/validate_patches.py --local path\to\unmodified\src
```

Remote mode downloads only the files Nadhr's patches touch, applies any upstream
patch that touches the same files, then applies Nadhr's patches with `git apply`.
